Transactions and two users changing the same data

Picture the last seat in a class and two cashiers selling it at the same moment. Each cashier looks at the seat map, sees one free seat and sells it. Both customers are told the seat is theirs, and neither cashier made a mistake.

A database has the same problem when two users change the same row. Everything so far assumed you were the only user. On enlistment morning you are one of nine thousand. Each user's connection to the database is called a session. Two sessions read the same row at the same moment, both decide there is room, and both write.

A transaction is a group of statements that the database treats as one unit. Step through the four attempts below and watch which ones still sell the seat twice.

Think first. Two students both look at the seat count and both see one free seat. Both enroll. What would the database have to do to stop the second enrollment? Write down one idea.

ACID: the four guarantees of a transaction
A
Atomicity

All of a transaction's statements happen, or none of them do. If the INSERT works and the UPDATE fails, the database undoes the INSERT. BEGIN and COMMIT give you this guarantee.

C
Consistency

Rules you declared stay true. A rule such as CHECK (slots >= 0), or a unique key, makes the database refuse any write that breaks it, whichever session sent the write and whatever the timing.

I
Isolation

How much two sessions running at the same time can see of each other's work. This is the guarantee that failed in the first attempt above. Many people assume the default settings protect them fully, and they do not.

D
Durability

After COMMIT returns, the change survives a power failure, because it has been written to disk. Of the four guarantees, this is the easiest to trust and the most expensive for the database to provide.

A transaction does not lock the row Wrapping the same statements in BEGIN and COMMIT looks like a fix, and it does not fix this. Atomicity means your own statements are applied together. It does not control whether another session read the row while you were deciding. At the default isolation level of Postgres, both sessions still see one free seat.

The fix is to tell the database what you need: lock the row while you decide, or write the decision as a single statement that the database can order for you.
