Under the Hood

This module follows one web request from your browser to a database, then shows how servers store data, handle crowds and run in the cloud. Each lesson is a few short steps: read the step, try the one thing it asks, then answer the check at the end.

What is a server?

A server is a program that waits for requests and answers them. Any computer can run one, including the laptop in front of you.

A sari-sari store is a store only while it is open and someone is behind the counter. With the shutter down, it is a room with shelves. A server works the same way. The computer is the room, and the server program is the shopkeeper who answers customers.

Think first. Is the laptop in front of you a server at this moment? Decide, then write down one thing you could check to find out.

Names and numbers

The host is a name because a number such as 18.141.62.7 is hard to remember and hard to change. Before anything else happens, the name has to be turned into an IP address, which is the number that identifies a machine on the network. That lookup is called DNS (the Domain Name System), and the first lookup costs a round trip of its own. "Round trips and latency" covers the cost.

Ports and encryption

By convention port 443 is for HTTPS and 80 is for HTTP, so browsers add them for you and hide them. The starter project for this course uses 8000, which has no special meaning. https means HTTP with the conversation encrypted (scrambled so only the two ends can read it).

Paths and query strings

The developers of the server decide the path. "HTTP verbs and status codes" covers how to design it well. The query string is part of the address, so it appears in server logs and browser history. Never put a password in it.

An IP address picks the machine, like a building. A port picks the program, like a unit number in it. The name localhost always means your own computer. Choose who is trying to open a tool on your laptop at port 8080.

Your laptop's several addresses

A laptop has one IP address for each network connection, and each address means something different. None of them is the address of your laptop on the internet. Data on a network travels in small pieces called packets. Click each address to see how far a packet sent to it travels.

127.0.0.1 is a real address, and nothing sent to it leaves the machine. The packet goes down into the operating system's network code and turns straight back up to another program on the same computer. It still works with the wifi unplugged.

192.168.x.x is a private range. Millions of homes use the same numbers at the same time, so the number alone cannot identify anything on the wider internet. Your router assigns these addresses and keeps track of which device asked for what.

The public address belongs to your router, and everyone in the building shares it. Many private addresses sit behind that one public address, so nothing on the internet can start a conversation with your laptop.

Why each row fails on a laptop

Your laptop's address is private, sits behind your router and is shared with the whole building. A home connection can be given a new address at any time. Most home internet providers block ports 80 and 443 on purpose, and these are the standard ports for HTTP and HTTPS. You close the lid, go to campus or change wifi, so the laptop is not always awake. Home plans are fast to download and slow to upload, and serving a website is all upload.

A hosting company sells a public address that does not change, an always-on machine with real upload capacity, and a network that leaves the needed ports open. How network messages are layered (protocol layers)

A network message is wrapped in layers, like a parcel. Each layer follows a protocol and adds a header to what it receives.

When you send a parcel by LBC, you put your item in a box, the branch adds a waybill with the destination, and a hub may stick on a new label. Nobody opens the box until it reaches the receiver. A network message travels the same way.

Think first. Guess how many bytes of headers the five layers add around a 24-byte message, such as a short form submission.
The total is 121 bytes: 38 (HTTP) + 29 (TLS) + 20 (TCP) + 20 (IP) + 14 (Ethernet) around the 24-byte message, 145 bytes in all. Students find it by adding the header bars in the next step.

Each layer wraps what it receives from the layer above in its own header and passes the result down. The receiving machine unwraps them in reverse order. A router reads only the IP header and writes a new Ethernet header for the next hop. Click each layer to see what its header adds.

Each packet carries up to 1,460 bytes of your data and 54 bytes of Ethernet, IP and TCP headers. Header overhead is the share of all bytes that are headers. A round trip is a message out and the reply back.

Press Send it to watch the packets leave. They do not all leave at once. TCP sends about ten, waits to hear that they arrived, then sends twice as many. A large reply therefore costs several round trips of waiting, in addition to the time the bytes take to move.

The 144-byte JSON reply in "Server or browser rendering" arrives with 54 bytes of headers, so 27% of that transfer is headers. The 280 KB JavaScript bundle (the file of code the browser downloads) in the same lesson needs several round trips for the same reason.

Why loading a page takes several round trips

A round trip is a message out and the reply back. A page load needs several of them before the server runs any of your code.

Before you order from a restaurant, you may call to ask whether it is open, wait for the answer, then call again to reserve a table. Each call has to go out and come back before the next one can start. A browser makes calls like these first.

Think first. Your code takes 40 ms whether the user is in Katipunan or in Berlin. Why does the page still load more slowly in Berlin?
Expected answer: every setup step needs at least one round trip, and each round trip takes longer over a greater distance. Server speed does not change that. Ask students to commit to a reason before they move the slider in the next steps.

The browser completes these steps in order. Each of the first three needs at least one round trip.

  2. TCP handshake: open a connection.
  3. TLS handshake: agree on encryption.
  4. Request: send GET /courses.
  5. Server handler: your code runs.
  6. First byte: the reply starts to arrive.

More detail

Real browsers send more headers than the samples in this lesson. These are common ones.

In requests

User-Agent: Mozilla/5.0 is a free-text description of the client program. Servers use it for statistics and to decide which files to send, and anyone can fake it.

Accept-Encoding: gzip, br says the client can unpack a compressed reply. If the server agrees, the body is sent 60 to 80 percent smaller, and compressing takes processing time on both ends.

Connection: keep-alive asks the server to keep the connection open because more requests are coming. This avoids paying the setup cost again.

Authorization: Bearer eyJhbGciOi... is proof of who you are. The text after Bearer is a token, a long random string that the server issued at login. Anyone who holds it can act as you, so it must only travel over TLS (encrypted connections).

In responses

Cache-Control: max-age=60 gives permission to reuse this answer for 60 seconds without asking again. A reused answer saves a whole round trip.

Choosing how much an endpoint returns

Both designs fail for the same reason: the endpoint was designed without knowing what the page does with it. One request per item costs a round trip each. One request for everything moves data nobody scrolls to. In both cases the fix is to add a parameter to the endpoint. GET /courses?codes=ITENT45,CSCI21 returns exactly the missing pieces in one trip. GET /enrollments?include=course lets the caller choose how much detail to receive. GET /courses?limit=20&offset=40 lets the caller ask for one slice, which is called pagination.

To decide, ask how many of the returned items will be looked at, and how soon the reader needs the first one. If every client loops over your list endpoint to fill in gaps, the endpoint returned too little. If most of what you send is never scrolled to, it returned too much.

Two properties tell you how risky a verb is to repeat. A verb is safe if it changes nothing. It is idempotent if sending it twice gives the same result as sending it once. Select each verb and read what happens when you send it twice.

Naming URLs

A URL should name a thing, such as courses or students, and the verb says what to do with it. A common first mistake is to put the action in the URL.

✕ Verbs inside the URL
  • GET /getCourses
  • GET /createEnrollment?student=5
  • POST /updateCourseName
  • GET /deleteStudent?id=5

Every new action needs a new URL, so the list keeps growing. The fourth one also changes data behind a GET. A search engine crawler (a program that follows links) could delete your students.

✓ Nouns in the URL, verb in the method
  • GET    /courses
  • POST   /enrollments
  • PATCH  /courses/ITENT45
  • DELETE /students/5

A small fixed set of verbs works with a growing set of nouns. Anyone who knows HTTP can guess your URLs without reading documentation. A predictable URL scheme is one of the main benefits of REST.

What REST asks of you

REST is a set of conventions for using verbs, URLs and status codes together. Model your system as resources: the nouns your users talk about, such as courses, enrollments and students. Give each resource a URL. Act on resources with the standard verbs. Let the status code report the outcome. Keep each request self-contained, so the server does not need to remember the previous one. This is called being stateless. Stateless servers are easier to copy onto many machines, as "Load balancers and scaling" shows.

Full example requests

GET /courses/ITENT45 HTTP/1.1 POST /enrollments HTTP/1.1 Content-Type: application/json {"student":"20-1234","code":"ITENT 45"} PUT /courses/ITENT45 HTTP/1.1 Content-Type: application/json {"title":"App Dev and Emerging Tech","units":3} PATCH /courses/ITENT45 HTTP/1.1 Content-Type: application/json {"units":6} DELETE /enrollments/8891 HTTP/1.1

POST needs protection that you build, such as a unique constraint (a database rule that rejects duplicates) or an idempotency key (a unique code the client sends with each request). "Payments and gateways" shows the second one at work.

Two pairs that are easy to mix up

401 and 403

401 Unauthorized means the server does not know who you are. The name is misleading, because the real meaning is unauthenticated. Send your login details and try again.

403 Forbidden means the server knows who you are and still says no. Better credentials will not help, because you are not allowed.

404 and 500

404 and 500 both look like a broken page to a user, and they point to different places to look.

404 means the URL names nothing, so check the request, the path and the id. 500 means the server code failed with an error, so read the server's error report (called a traceback) and ignore the page itself.

A web page can be built on the server or in the browser. The choice changes how fast the first screen appears and how much data travels.

A restaurant can print a fresh menu for every customer, or hang one menu board and change only the prices that change. A web server faces the same choice. It can build every page itself, or send one page once and let the browser update it.

Server-rendered page, the older model

The server fills in a template (a page layout with blanks), produces finished HTML (the language that describes a web page), and sends a complete document. The browser discards the old page and draws the new one. The enlistment system works this way.

click → request → server renders → full HTML → repaint first screen: fast, the HTML arrives ready to draw each later click: another full page

Single-page app, the newer model

The first load fetches an almost empty shell and a large bundle of JavaScript (code that the browser runs). After that, each click fetches JSON, and the browser updates only the parts of the DOM that changed. The DOM is the browser's live model of the page. Nothing else reloads.

first load → shell + bundle → fetch JSON → build DOM first screen: slower, nothing shows until the bundle runs each later click: a few KB of JSON and no redraw of the rest

Keep 15% of the RAM free. Memory that looks unused holds the disk cache, which is recently read files kept in RAM for fast access. When no RAM is left, the system starts swapping, which means using the disk as extra memory. The disk is roughly a thousand times slower.

Multi-AZ saves each write in both data centers before confirming it. This is called synchronous replication, and it works because the buildings are milliseconds apart.

Multi-region copies each write to Tokyo after confirming it. This is called asynchronous replication, and the newest writes can be lost if the primary region fails.

Recovery time and recovery point

The recovery time objective (RTO) is how long until you are back. The recovery point objective (RPO) is how much data you accept losing. Choose both before an outage, because afterward they are chosen for you.

Every user of your capstone is in Metro Manila, so choose Singapore. Use multi-AZ, which means two data centers in one region, if the provider offers it by default. It costs little and protects against a data center failure. Skip multi-region, which doubles the cost and needs code to resolve conflicting writes.

You can now choose a region setup for a project.

More detail

How to tell them apart

Entity: a person, place, object, event or concept the organization keeps data about. It has many examples, and each one can be told apart from the others.

Attribute: a property of an entity. It describes nothing on its own and only makes sense when it is attached to an entity.

The REA pattern: resources, events and agents

Most business systems record transactions with one pattern, called REA. Because it repeats, you rarely design a schema from nothing.

At a sari-sari store, the owner hands over a bottle of soda and takes 20 pesos, or writes the amount in the utang notebook to be paid later. The goods going out and the payment coming back are two separate records.

Think first. Think of a purchase you made this week: what was given, what came back, and who was on each side?

More detail

The three parts of REA

Resource: the thing of value, such as a seat, a book, an item of stock or cash. The event moves it.

Event: a record of something that happened at a moment and changed who holds the resource. Events are usually the tables with the most rows.

Agent: a person or organization on one side of an event. Usually one is inside your organization and one is outside it, and you need to record both.

Where the foreign keys sit

One resource appears in many events, and one agent takes part in many events. So the event table holds both foreign keys, following the rule from "Relationships" that the foreign key goes on the many side.

Why there are two events

A seat is given and money is taken. A book goes out and comes back. If you model only the half you were asked about, the system cannot answer where the money went.

The hardest business questions are gaps between two events that should have paired: unpaid enrollments, overdue books, orders delivered but not billed. "Payments and gateways" shows the same problem on the network side.

The dashed line joins two events that pair up, such as an enrollment and its payment. One payment can cover several enrollments, and one enrollment can be paid in installments. So the pairing is many-to-many and needs a table of its own. That table records how much of each payment applies to each enrollment.

Atomicity

If the INSERT works and the UPDATE fails, the database undoes the INSERT. BEGIN and COMMIT give you this guarantee.

Consistency

A rule such as CHECK (slots >= 0), or a unique key, makes the database refuse any write that breaks it, whichever session sent the write and whatever the timing.

Isolation

Durability

The four families, and what "schema" means in each

The common split between SQL and NoSQL databases is a split in where the schema is enforced. Both families have a schema. In a relational database, the database enforces it. In the others, your code does.

Structured: the database enforces the schema
Relational

Tables with fixed columns and declared types. The schema is written down once, and the database rejects any data that does not fit it. Joins let you ask questions you did not plan for.

Postgres · MySQL · SQL Server · Supabase

The entities, attributes and relationships from "Entities and attributes" and "Relationships" still apply. A document database does not remove them.
