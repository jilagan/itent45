Online payments and payment gateways

At a store counter you pay the cashier and get a receipt or claim stub. The shop does not process your card itself, because the cashier's terminal talks to the bank.

An online checkout works the same way. The shop's server hands the payment to a payment gateway, a company such as PayMongo, Stripe or Xendit that handles card payments for shops, and gets back a token, which works like a claim stub. The analogy stops in one place: online, the customer's browser sends the card straight to the gateway, and the shop's server never sees it.

Until now your server has only answered requests. In a checkout it also sends them, over the same HTTP and with the same verbs and status codes described in "HTTP verbs and status codes". Several parties each hold a piece of one transaction, and each can fail separately. This panel follows one payment, compares message formats, and covers double charges.

Why the card skips your server The browser sends the card directly to the gateway and gets back a token, which is an opaque code that stands for the card. Your server only handles the token. This is deliberate. If card numbers passed through a machine you own, that machine would fall under PCI DSS (the card industry's security rules), and so would every system it talks to. With a token, that burden stays with the gateway, which is set up to meet those rules.
Step 9 reverses the roles. The gateway calls your server, so your API is the server in that exchange. The signature header is the only check that stops anyone on the internet from marking their own order paid.
Why every message in the flow is JSON

No person reads these messages. Two programs at two companies are exchanging facts, and JSON was designed for that. SOAP is an older message standard that is written in XML. The same charge request is shown below in three formats so you can compare them.

When XML is still the right choice JSON carries values and no rules. It cannot state that amount must be a positive integer or that currency must be a real ISO code (a standard currency code such as PHP), so each check is written in application code on both sides. An XML schema states the rules once, and a parser enforces them before your code runs. XML-DSig, a standard for digital signatures, can sign the whole document. When the thing being exchanged is money between institutions, that is worth six times the payload. Several Philippine banks still offer exactly this. If your capstone connects to a real bank and not a modern gateway, expect SOAP and plan about a week for the integration.

How a slow gateway affects server capacity

Capacity here means requests per second (rps): the number of workers divided by the seconds each request takes. How to measure it is covered later in "Server capacity".

Charging inside the request
handler 40 ms + gateway 800 ms = 840 ms 4 workers ÷ 0.840 s = 4.8 rps
Charging on a queue, confirming by webhook
handler 40 ms, gateway call moved off the path 4 workers ÷ 0.040 s = 100 rps

In the second case, the gateway call goes on a queue, which is a waiting list of jobs that a separate process works through, and the gateway reports the result later by webhook. If your server waits for the payment gateway, your site is as slow as the gateway. The twenty times higher capacity here comes from moving the call out of the request. The same change solves Card C, covered later in "Group exercises".
