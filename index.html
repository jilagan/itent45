What is a server, actually?

You have heard the word your whole life and almost nobody is taught what it means. It is worth ten minutes, because every panel after this one assumes it. The short version: a server is not a kind of computer. It is a job a computer is doing right now, and any computer can do it, including the one in front of you.

Ask the room. Hands up if you could point at a server. Now: is your laptop one? The honest answer is that it depends on what is running on it at this moment.

The word means two different things
The machine

A physical computer somewhere. It has a processor, memory and a network cable. Panel 17 is entirely about this one, and about how little of it you actually get.

The program

Software running on that machine, sitting in a loop, waiting for someone to connect. nginx, gunicorn, node, or the twenty lines in teaching_server.py.

When somebody says the server is down they almost always mean the second one. The machine is usually fine. A program on it stopped waiting.

An IP address says which machine. A port says which program on it.

Think of the IP as the building and the port as the unit number. One building, many units, and a delivery needs both.

127.0.0.1, also spelled localhost, is a special one. It always means this machine, right here, so it means something different on every computer that types it.
Your laptop has more than one IP address

One per network interface, and they mean different things. None of them is the address of your laptop. Click each and watch how far a packet sent to it actually travels.

Why this trips people up

127.0.0.1 is a real address, and nothing sent to it ever leaves the machine. The packet goes down the operating system's network code and turns straight back up into another program on the same computer. Unplug the wifi and it still works, which is the giveaway.

192.168.x.x is a private range. Millions of homes use the same numbers at the same moment, so the number alone cannot identify anything on the wider internet. Your router hands these out and keeps track of which one asked for what.

The public address belongs to your router, not to your laptop, and everyone in the building shares it. That translation, many private addresses behind one public one, is why nothing on the internet can start a conversation with your laptop.

So can you just host the capstone on your laptop?

This question comes up every year and the answer is more interesting than a flat no. Your laptop is a server, in the sense that matters for the definition. Serving the public internet from it needs six things, and it has one of them.

02 — Encapsulation

Your message travels inside a stack of envelopes

A protocol is just an agreement about the shape of a message. Each layer takes what it was handed, wraps it in its own header, and passes it down. The receiving machine unwraps in reverse. Nobody talks across layers. Each layer only talks to its counterpart on the far end.

THE PAIR EVERYONE MIXES UP

401 Unauthorized is badly named. It means unauthenticated. The server does not know who you are. Send credentials and try again.

403 Forbidden means the server knows exactly who you are, and the answer is still no. Better credentials will not help; you simply are not allowed.

THE FORK THAT SAVES YOU AN HOUR

404 and 500 look equally broken to a user, and they send you to completely different places.

404 means your URL named nothing, check the request, the path, the id. 500 means your code raised an exception, stop reading the front end and go and read the traceback.

Naming things: the mistake almost everyone makes first
✕ Verbs baked into the URL
  • GET /getCourses
  • GET /createEnrollment?student=5
  • POST /updateCourseName
  • GET /deleteStudent?id=5

Every new action needs a new URL, so the list grows without end. Worse, the fourth one changes data behind a GET. So a search engine crawling your site can delete your students.

✓ Nouns in the URL, verb in the method
  • GET    /courses
  • POST   /enrollments
  • PATCH  /courses/ITENT45
  • DELETE /students/5

A small fixed set of verbs against a growing set of nouns. Anyone who knows HTTP can guess your API without reading documentation. That guessability is most of what REST is worth.

The answer is usually neither extreme Two failure modes, opposite directions, same cause: designing the endpoint without knowing what the page does with it. One request per item pays a round trip for each. One request for everything pays for data nobody scrolls to. The fix in both cases is a parameter rather than a new endpoint. GET /courses?codes=ITENT45,CSCI21 fetches exactly the missing pieces in one trip. GET /enrollments?include=course lets the caller say how much detail it wants. GET /courses?limit=20&offset=40 lets it ask for a slice.

The question that settles it is not about REST. It is how many of the things you return will actually be looked at, and how soon the reader needs the first one. If every client immediately loops over your list endpoint to fill in gaps, it returned too little. If most of what you send is never scrolled to, it returned too much.
What REST actually asks of you Model your system as resources. The nouns your users talk about: courses, enrollments, students. Give each one a URL. Act on them with the standard verbs. Let the status code carry the outcome. Keep each request self-contained, so the server needs no memory of the last one. Which is the same statelessness that panel 19 shows you cannot scale without.

07 — Who builds the page

The server sent data. Something still has to turn it into a page.

Panel 06 ended with a response that was identical for every client. That response was data, not a page, which leaves a question nobody asked out loud: who assembles the thing a person actually looks at, and where does that work happen? There are two answers, they were popular in different decades, and the choice changes what travels over the wire, how fast the first screen appears, and how much work your server is doing per visitor.

Ask the room. When you click a link on a normal website, does the browser throw away the whole page and get a new one? On some sites yes, on others no. You can usually tell by watching the tab spinner.
Server-rendered · the older model

Every click fetches a whole new page

The server runs your template, produces finished HTML, and sends a complete document. The browser throws away what it had and draws the new one. The enlistment system works this way.

click → request → server renders → full HTML → repaint first screen: fast, the HTML arrives ready to draw every click after: another full page, every time
Single-page app · the newer model

One page, then only data moves

The first load fetches an almost-empty shell and a large bundle of JavaScript. After that, clicks fetch JSON and the browser rewrites the parts of the DOM that changed. Nothing else reloads.

first load → shell + bundle → fetch JSON → build DOM first screen: slower, nothing shows until the bundle runs every click after: a few KB of JSON, no repaint of the rest

Up to now your server has answered requests. Why the card skips your server The browser sends the card straight to the gateway and gets back an opaque token. Your server only ever handles that token. This is deliberate: the moment card numbers touch a machine you own, that machine falls inside PCI DSS scope, and so does every system it talks to. Handling a token instead keeps that burden with the people whose entire business is carrying it.
Roles invert at step 8. The gateway calls you. Your API is the server in that conversation, and the signature header is the only thing standing between you and anyone on the internet marking their own order paid.
Why is every message in that flow JSON?

Nothing in this exchange is ever looked at by a person. Two programs at two companies are stating facts to each other. That is the situation JSON was shaped for, and it is worth seeing the alternatives written out before accepting it. Here is the same charge request, three ways.

When XML is still the right answer JSON carries values. It has no way to state that amount must be a positive integer, or that currency must be a real ISO code, so every one of those checks lives in somebody's application code and gets written again on both sides. An XML schema states them once and a parser enforces them before your code runs, and XML-DSig can sign the document itself rather than the bytes around it. When the thing being exchanged is money between institutions, that is worth six times the payload. Several Philippine banks still expose exactly this, so if your capstone touches a real bank rather than a modern gateway, expect SOAP and budget a week for it.

17 — What a server is actually holding

Before anything of yours runs, the box is already half full

A server is a computer with a fixed amount of RAM, and your application is only one of the things living in it. The operating system was there first. So was the web server, and often the database too. Whatever is left over is what you get to spend on workers, and each worker costs far more than students expect.

Ask the room. Your laptop has 8 GB. How much of it is free right now, before you open anything? Same question, same answer shape, for a server.
Memory budget

What one worker actually is

When you run gunicorn --workers 8, you do not get eight threads sharing one Django. You get eight separate operating system processes, and each one loads its own Python interpreter, its own copy of Django, and its own copy of every library you imported. Pandas alone can cost 100 MB before a single request arrives.

That is why the per-worker number below is the one that decides how big your box has to be. It is paid once per worker, whether or not anyone is using the site.

Threads are cheaper but weaker. Threads inside one process share all that memory, so twenty threads cost almost nothing extra. But Python's global interpreter lock means they cannot run Python code at the same time on different cores. Threads are for waiting on the database. Processes are for actually computing.

19 — Many machines · overlaps Module 6

More machines, and the thing in front that makes them useful

Panel 18 ended with one saturated box, and there are only two ways past that: buy a bigger box, or run several. The second needs a load balancer, and it asks something of your code in return. Once you have it, fixing a bottleneck stops being one decision and becomes a sequence of them, because every fix hands you a new constraint.

Ask the room If two machines each serve 80 requests a second, how does a browser know which one to talk to? It does not, and it must not. Something in front has to decide.
Option 1 · scale vertically

Buy a bigger machine

More RAM, more cores, same single box. This is what panel 17 was about, and it needs no code changes at all, which is why it is always the first thing to try.

Runs out. There is a biggest machine you can rent, and the price climbs faster than the capacity does. One box is also one thing that can fail.
Option 2 · scale horizontally

Run the same machine several times

Identical copies of the box from panel 18, with something in front deciding who gets each request. No ceiling in principle, and a dead machine stops being fatal.

Costs you a precondition: every copy must be able to answer any request, because you no longer control which one gets it.
What the thing in front actually does

A load balancer is a reverse proxy: one address the world talks to, which accepts each connection and opens a second one to whichever backend it picks. Clients never learn the backends exist. It also polls each one on a health endpoint every few seconds, and stops sending work to anything that fails to answer.

24 — Module 6 · monolith and microservices

Scaling out is not the same as splitting up

Panel 19 gave you six machines. Every one of them was an identical copy of the same application. That is a monolith, scaled horizontally, and it is what most systems should be. Splitting up is a different move on a different axis: several different things, each sized for its own appetite. Panel 20 already showed you a candidate, when browsing the catalog and reserving a seat turned out to want opposite things from the same box.

Ask the room If one part of your app needs 400 MB and the rest need 90, how much memory does a copy of the monolith need? Now multiply that by every copy you run.
Monolith · one app, many copies

Every copy can do everything

Any machine can serve any request, so the load balancer does not care which one it picks. Simple to deploy, simple to reason about, and one stack trace when something breaks. The cost: every worker must be sized for the heaviest thing it might be asked to do.

22 — Module 4 · cloud economics

From asset-heavy to asset-light

The technical argument for cloud is elasticity. The argument that actually gets it approved is an accounting one. Owning servers is capital expenditure. A large sum spent up front, capitalised and depreciated over years, committed before you know what you need. Renting them is operational expenditure. A monthly bill for what you actually used, expensed as you go.

Ask the room the enlistment system needed seven servers for the twenty minutes of enlistment morning. What were those seven servers doing on the other 364 days?
Asset-heavy · CapEx

You own the infrastructure

Servers, data centre, enterprise licences. A large sum committed up front and depreciated over several years.

Predictable but inflexible. You must guess your peak years ahead, and you are wrong in one of two expensive directions.
Asset-light · OpEx

You rent it by the hour

Compute time, storage, SaaS subscriptions. Expensed monthly, attributable to the thing that caused it.

Lower entry cost and elastic, but the meter never stops. A forgotten test environment bills you every month until someone notices.

09 — Module 5 · what the words mean

Before you draw anything, sort the nouns

A data model starts as a pile of nouns from a conversation with whoever wants the system. Three of those nouns are three different kinds of thing, and mixing them up is the single most common way a first diagram goes wrong. An entity is a thing worth keeping data about. An attribute is a fact that describes one. An instance is one actual specimen. Sort these.

Ask the room. Is Room an attribute of a class, or a thing in its own right? Both answers are defensible, and which one you pick decides whether you can ever ask what else is scheduled in SOM 407.
How you tell them apart
Entity — a person, place, object, event or concept the organisation wants to keep data about. It has many possible specimens, and each has something that tells it apart from the others.

Attribute — a property of an entity. On its own it describes nothing; it only makes sense attached to something.

Instance — one specimen. Not a thing you design, a thing you store. If you find yourself drawing a box around it, you have gone wrong.
Events are entities too, and students always miss them Student and Course are easy. Enrolment is the one that gets left out, because it does not feel like a thing, it feels like something that happened. But it has a date, a status and a grade, and none of those belong to the student or to the course. The moment two entities need facts that describe the pairing rather than either side, the pairing is an entity. Panel 10 is what happens to your tables when you notice.
10 — Module 5 · relationships

Cardinality is not diagram decoration. It decides your tables.

Two entities, one relationship between them, and a question: how many of each side can pair with how many of the other? The answer is one of three, and each produces a different set of tables. Get it wrong on the diagram and you will discover it later, in production, when somebody needs a second one of something you allowed only one of.

Ask the room. Can a student take more than one course? Can a course have more than one student? Two yeses, and the tables you are about to draw are not the tables you expected.
What each one costs you
The junction table is where the interesting columns live Students meet many-to-many and treat the extra table as bookkeeping, a nuisance the database imposes. It is the opposite. That table is the only place a date, a status or a grade can sit, because those facts describe the pairing and belong to neither side. Panel 09 called Enrolment an entity for exactly this reason. The diagram was telling you a table was missing before you knew you needed one.
11 — Module 5 · a pattern that repeats

Most business systems are the same six boxes wearing different words

Once you have drawn a few models you start noticing that they rhyme. Something of value changes hands. An event records it. People are on both sides. And the event almost never travels alone, because value moving one way is usually paid for by value moving the other. That observation has a name, REA, and it is the reason you rarely design a schema from nothing.

Ask the room. Pick any transaction you did this week. What was given, what came back, and who was on each side? If you can answer that, you have just drawn the model.
Duality is not a tidy one-to-one

It is tempting to read the dashed line as every enrolment has its payment, and to build a column for it. That works until the first student pays in instalments, or settles four subjects with one transfer. The pairing is many-to-many, which means panel 10's rule applies to it: the duality needs a table of its own, and that table has to carry how much of this payment applies to that enrolment.

Some events genuinely have no partner, and that is not a gap A scholarship waiver, a spoiled batch, a donated seat, a book written off after a flood. A resource decreases and nothing comes back, legitimately. If your reconciliation treats every unpaired event as an exception it will cry wolf forever, and people will stop reading it.

So decide once, deliberately, which events are expected to pair and which are not, and record that in the model rather than in someone's head. This pair is missing and this one never had a pair are different facts, and only one of them is a problem.
Where to put the boxes

Nothing forces you to lay a diagram out one way rather than another, so most people do not, and the result is a plate of spaghetti nobody can read a second time. There is a convention that costs nothing: point every crow's foot up and to the left. Because the crow's foot always sits on the many side, and the many side is almost always the thing that happens, the diagram sorts itself.

The three letters
Resource — the thing of value. A seat, a book, an item of stock, cash. It is what the event moves.

Event — the thing that happened, at a moment, which changed who holds the resource. Events are the rows you will have most of.

Agent — who was on each side. Conventionally one is inside your organisation and one is outside it, and you almost always need both.
Why two events, not one
The pairing is called duality, and it is the part students skip. A seat is given and money is taken. A book goes out and comes back. Modelling only the half you were asked about is how systems end up unable to answer where the money went.

Duality is also where your hardest questions live: unpaid enrolments, overdue books, delivered-but-unbilled orders. Every one of those is a gap between two events that should have paired and did not.
Universal data models: somebody has already drawn yours Because the shape repeats, the industry stopped redrawing it. Universal data models are published templates for common domains, and every framework you will use ships opinionated versions of them, whether or not it says so. Django's auth tables, a Supabase starter schema, an e-commerce boilerplate: those are all somebody else's answer to a model you were about to draw badly.

Use them, and read them. The value is not the time saved. It is that a template shows you which entities somebody discovered the hard way, and the one you would not have thought of is usually the event in the middle.

13 — Module 5 · transactions

One seat, two students, and both of them get it

Everything so far assumed you were the only person talking to the database. On enlistment morning you are one of nine thousand. Two sessions read the same row at the same moment, both decide there is room, and both write. Neither did anything wrong. Step through it, then try the fixes, and notice which one does not work.

Ask the room. If both students saw one seat free, which of them made the mistake? Neither. That is the point, and it is why the database has to be the one that decides.
What this attempt does
The four letters, and which one you just broke
A
Atomicity

All of it happens or none of it does. If the INSERT succeeds and the UPDATE fails, the database undoes the INSERT. This is the one BEGIN and COMMIT actually give you.

C
Consistency

Rules you declared stay true. A CHECK (slots >= 0) or a unique key will refuse a write that breaks them, no matter which session sent it or how well timed it was.

I
Isolation

How much two sessions running at once can see of each other. This is the one that was broken above, and the one people assume they get for free. They do not.

D
Durability

Once COMMIT returns, it survives the power going out. Written to disk, not sitting in memory hoping. The cheapest of the four to believe in and the most expensive to provide.

A transaction is not a lock, and this is the mistake to expect Wrapping the same four statements in BEGIN and COMMIT feels like it should fix this, and it does not. Atomicity says your own statements land together. It says nothing about whether somebody else read the row while you were thinking. At the isolation level almost every database ships with by default, both sessions still see one free seat.

What fixes it is telling the database what you actually need: lock the row while you decide, or write the decision as a single statement it can serialise for you. Panel 19's enlistment morning is nine thousand people doing this at once, and panel 08's idempotency key is the same problem arriving over HTTP.

The two families, and what "schema" means in each

The split people mean by SQL and NoSQL is really a split about where the schema is enforced. Both have one. Only one of them makes the database responsible for it.

Structured · the database enforces it
Relational

Tables with fixed columns and declared types. The schema is written down once and the database refuses anything that does not fit. Joins let you ask questions you did not plan for.

Postgres · MySQL · SQL Server · Supabase
Unstructured · your code enforces it
Document

Records are self-describing documents. Two documents in the same collection can have different fields, so a typo becomes a new field rather than an error. The schema still exists, it just lives in your application.

MongoDB · Firebase · DynamoDB
Unstructured · barely a schema at all
Key-value

A key, a blob, and nothing else. Extremely fast and extremely dumb. Used as a cache in front of something else more often than as a system of record.

Redis · Memcached
Unstructured · a different question
Graph

Stores the relationships as first-class things rather than as foreign keys. Worth knowing exists. Reach for it when the question is "how is this connected to that", several hops deep.

Neo4j · Neptune
