Online payments and payment gateways

A payment gateway handles card payments for shops. This lesson follows one payment from the shopper's browser to the bank.

At a store counter you pay the cashier and get a claim stub. The shop does not process your card itself, because the cashier's terminal talks to the bank. Online, the shop's server hands the payment to a payment gateway and gets back a token, which works like the claim stub.

Think first. When you type your card number into a checkout page, which machines does the number pass through on its way to the bank? List them.
Most students include the shop's server in their list. The correct list leaves it out. Ask them to say why that matters for the shop.

Four parties take part in a checkout: the shopper's browser, your server, the gateway and the bank. Press Play and watch where the card number goes. Your server receives only a token.

Why the card skips your server

The browser sends the card directly to the gateway and gets back a token, which is an opaque code that stands for the card. Your server only handles the token. If card numbers passed through a machine you own, that machine would fall under PCI DSS (the card industry's security rules), and so would every system it talks to. With a token, that burden stays with the gateway, which is set up to meet those rules.

Step 9 reverses the roles

The gateway calls your server, so your API is the server in that exchange. The signature header is the only check that stops anyone on the internet from marking their own order paid.

Why every message is JSON

No person reads these messages. Two programs at two companies are exchanging facts, and JSON was designed for that. SOAP is an older message standard that is written in XML. The same charge request is shown here in three formats so you can compare them.

When XML is still the right choice

JSON carries values and no rules. It cannot state that amount must be a positive integer or that currency must be a real ISO code (a standard currency code such as PHP), so each check is written in application code on both sides. An XML schema states the rules once, and a parser enforces them before your code runs. XML-DSig, a standard for digital signatures, can sign the whole document. When the thing being exchanged is money between institutions, that is worth six times the payload. Several Philippine banks still offer exactly this. If your capstone connects to a real bank and not a modern gateway, expect SOAP and plan about a week for the integration.

Why a double charge happens

A POST is not idempotent, so each press can create a separate charge. "HTTP verbs and status codes" explains the term. The key is a UUID, which is a random unique code.

What the request looks like

Your server has a fixed number of workers. Capacity is the number of workers divided by the seconds each request takes. Compare a request that waits for a slow gateway with one that puts the call on a queue.

How a slow gateway affects server capacity
Charging inside the request
handler 40 ms + gateway 800 ms = 840 ms 4 workers ÷ 0.840 s = 4.8 rps
Charging on a queue, confirming by webhook
handler 40 ms, gateway call moved off the path 4 workers ÷ 0.040 s = 100 rps

If your server waits for the payment gateway, your site is as slow as the gateway. Moving the call out of the request gives twenty times the capacity here.
