One API for the web, iOS and Android

A restaurant kitchen can serve dine-in customers, the drive-thru window and a delivery app. The kitchen prepares the same order for all three, and each channel presents it in its own way.

A web page, an iPhone app and an Android app can work the same way. They all use one backend, which is the server and database that hold the data. They reach it through an API (application programming interface), a set of URLs that return data.

The server does not care whether the caller is a browser, an iPhone or an Android app. It sends the data as JSON, a plain-text format for data, and each client displays it however it likes. This panel covers the three clients, a system that has no API, and what happens when an API changes.

What REST stands for REST stands for Representational State Transfer. The server holds the data. When a client asks for it, the server sends a representation of that data, which here is JSON text. What the client does with it is up to the client: a table, a list, a scrolling view in a phone app, or a printout. The server never needs to know.

Older systems, such as the enlistment system, return finished web pages that contain both the data and the layout. These pages are built on the server, and the business logic (the rules for what the system does) sits inside the code that writes each page.

All the data a mobile app needs is in the HTML response on the left, mixed with table widths, CSS class names (labels that control appearance) and a decision about column order. An iOS app cannot use that response directly. It would have to scrape it, which means reading HTML written for a browser and hoping the layout never changes. The layout changes often.

Why teams build it this way With one kind of client, browsers only, server-rendered HTML was the fastest correct design. The cost shows up years later, when a second kind of client arrives and there is nothing for it to call. Adding an API later means going into the page-generating code and pulling the business logic out of the markup. Teams often keep the old design because it still works.

Once phones call your API, you do not control when clients update. Web users get new code the next time they reload the page. A person with your iOS app has to open the store and choose to update, and some never do. Old copies keep calling your API for months. Rule for changing an API If you cannot update the clients, add freely and remove almost never. When you must break something, publish the new version at a new path (/api/v2/courses) and keep the old one running until few users remain on old versions. Another option is to keep the old field next to the new one and stop documenting it.
