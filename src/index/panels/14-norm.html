Normalization: storing each fact once

Normalization means storing each fact in one place only. Every other place that needs the fact points to it.

Suppose you keep a class list in Excel and type the course title on every student's row. When the title changes, you must fix every row, and one missed row leaves two titles for the same course. A better layout is a second sheet that lists each course once, with each student row pointing to it.

Think first. Suppose each student row holds only a course number, and titles sit on a course sheet. What must you do to print one student's schedule with titles?
The answer is to look up each course number on the course sheet, which the database calls a join. Collect a few answers before anyone opens the next step. Some students will say it is more work, which is true and is covered in the last step.

Change how many students are enrolled

The flat table repeats the title once for each enrollment, and the split version stores it once. Raise the slider to 400 and think about running a script that makes 400 separate changes to a live database.

Store each fact once, and point to it from every place that needs it. A title kept in one row has one value. A title copied into four hundred rows can differ from row to row, and nothing in your code will notice, because each row is valid on its own.

The cost of splitting

Both designs are valid. The flat table can show one student's schedule without a join, which is why people propose it, and the split design needs the join each time it reads. The size of that cost is measured in "The N+1 query problem".

AI-generated schemas

A schema generated by an AI tool can work and still repeat facts like this. The tool will not warn you.
