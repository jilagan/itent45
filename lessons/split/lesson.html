One application or many services?

Software can be built as one application or as several small ones. This lesson compares the memory each design needs and what splitting costs.

You open a food delivery app at dinner time. The restaurant list loads at once. You press Place order and the screen waits, then shows an error. You go back, and the restaurant list still works.

Think first. If the app runs as 24 workers that can each do every task, and the heaviest task needs 400 MB, how much memory do the workers need in total?
The answer is 24 times 400 MB, which is 9,600 MB or about 9.4 GB. Most of that memory sits unused, because few workers ever do the heavy task. The next step shows the same effect.

How the columns are sized

Both columns use 4 workers per machine, as in Server capacity. The workers differ in what each one must be able to do.

In the monolith, any machine can serve any request, so the load balancer can pick any of them. The application is simple to deploy, and a failure produces one stack trace, which is the error report that shows where in the code the failure happened. Every worker needs enough memory for the heaviest task it might be given.

The restaurant list service never loads the PDF library, so it never needs 400 MB. You can add copies of the slow part without paying for extra copies of the fast parts.

Splitting can save memory at high load. It also adds four costs that start on the first day you split.

Calls cross the network

A call can be slow, time out, or fail after the work is done.

Services change at different times

Services deploy at different times, so a message change must add fields and remove none.

Every call needs retry rules

Each call needs a timeout, retries and an idempotency key, so retries are safe.

One failure, several logs

Follow a failure across services with a shared trace ID on every request.

The assumptions behind the figures

Each call to another service takes about 3 ms longer than the same work done inside one program. The extra time covers opening a connection, converting data to a message and back (serialization), and the network. That figure is for a good day inside one data center.

Each service is up 99.9% of the time, which is the share of time it is working, and 1% of its calls are slow. These are good numbers for one service. The widget in this lesson shows what they become when one request needs several services.

A similar problem one layer down

The problem in The N+1 query problem has the same pattern: many small requests where one would do. A database option such as select_related cannot fix it here.

Build the monolith, with its parts in separate modules and no code that reads another module's tables. Then a boundary exists if you ever need to split. Split a part only when its needs differ and you can say why. If two services call each other on every request, treat them as one service.

You can now decide whether a part of a project should be its own service.

More detail

Distributed monolith

Splitting an application whose parts still need each other on every request produces a distributed monolith. It has all the costs of separation and all the dependence between parts, so it is slower, fails more often and is harder to debug than the single application you started with.

Split only where the parts do not need each other. That depends on your business domain.

Why most small projects stay as one application

At low load, four services use more memory than one monolith, and most small projects run at low load. Most microservices failures start with a team that split before it had a reason, and paid the four costs of splitting to solve a scaling problem it did not yet have.
