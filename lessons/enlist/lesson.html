Case study: enlistment day

On enlistment morning thousands of students use the same system within minutes. This case study tests which part of the system runs out of capacity first.

On enlistment day thousands of students crowd around the schedule board, and each needs only a few seconds to read it. Only one window can reserve seats, and it must give the last seat in a section to exactly one student.

Think first. A university can add web servers in minutes, yet enlistment is still slow at 8:00 AM, so where is the slowdown?
Ask for a show of hands: who has seen the enlistment system slow down on enlistment morning? Listen for students who blame the web servers, and steer them toward seat reservation.

More detail

A cache is a fast store of recent answers, so the database is asked less often. Replicas are read-only copies of the database. Both can serve browsing, which is mostly reads. Seat reservations cannot be cached and cannot be spread across replicas, because two students must never get the same last slot.

The model assumes 15 requests per enlistment session, 3 of them reservations.

Change the size of the crowd. Rates are in requests per second (rps) for the web tier and database operations per second (ops/s) for the database. Without staggering, the start bursts at about 6 times the average rate, because everyone clicks at 8:00:00.

The shape is typical of student enlistment systems. Every number here is made up for teaching.

Autoscaling fixed the web tier. The database is still one primary, because every seat reservation must be exactly right. Two changes help without buying hardware. Staggering flattens the peak, and sending browsing to read-only copies leaves the primary with only reservations.

You can now say which tier fails first on a busy day and how to relieve it.

More detail

Such systems have often run on a handful of application servers with a single relational database behind them. Many have since moved to cloud hosting, where web tier capacity can be bought in minutes. Load balancers and scaling showed that once the web tier is fixed, the database is the next bottleneck.

On-premise means the servers are owned and run by the university. The hardware was fixed, so adding capacity meant buying and installing a machine. Autoscaling means the web tier grows automatically when the load rises.
