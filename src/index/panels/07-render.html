Building the page: on the server or in the browser

A web page can be built on the server or in the browser. The choice changes how fast the first screen appears and how much data travels.

A restaurant can print a fresh menu for every customer, or hang one menu board and change only the prices that change. A web server faces the same choice. It can build every page itself, or send one page once and let the browser update it.

Think first. When you click a link on a site you use, does the whole page reload or only part of it? Watch the browser tab for a loading spinner.
On some sites the whole page reloads and on others it does not. Ask students to name one site of each kind and say how they could tell.

More detail

Server-rendered page, the older model

The server fills in a template (a page layout with blanks), produces finished HTML (the language that describes a web page), and sends a complete document. The browser discards the old page and draws the new one. The enlistment system works this way.

click → request → server renders → full HTML → repaint first screen: fast, the HTML arrives ready to draw each later click: another full page

Single-page app, the newer model

The first load fetches an almost empty shell and a large bundle of JavaScript (code that the browser runs). After that, each click fetches JSON, and the browser updates only the parts of the DOM that changed. The DOM is the browser's live model of the page. Nothing else reloads.

first load → shell + bundle → fetch JSON → build DOM first screen: slower, nothing shows until the bundle runs each later click: a few KB of JSON and no redraw of the rest

The model uses 45 KB of HTML per server-rendered page, a 280 KB bundle for the single-page app, and 4 KB of JSON per navigation after the first load. Stylesheets and scripts are counted once because the browser caches them, which means it keeps a copy.

Most people leave after one or two pages. Drag the slider there and check which model wins. A single-page app also suits a brochure site (a site of a few fixed pages) poorly.

Decide which kind of capstone project yours is. If it is mostly pages that people read, server-rendered pages have fewer parts and a faster first screen. If people use it for twenty minutes, clicking around, a single-page app makes up its download cost after about seven pages.

More detail

What most student projects do

Most student projects are the first kind and get built as the second kind, because tutorials show that approach. Django (a Python web framework) builds server-rendered pages by default. Choose based on how long users stay and how many pages they open.

What each choice costs elsewhere

Rendering moves to the user's device

A single-page app has the browser build the page, so your server no longer does that work. That raises the capacity ceiling covered in "Server capacity", using hardware you did not buy.

→ See "Server capacity". It uses the user's battery.
The first screen is slower

Server-rendered HTML is ready to draw when it arrives. A bundle has to download, load and run before anything appears, and then it fetches its data.

→ See "Round trips and latency". The cost is now on the client.
You rebuild what the browser did for free

The back button, scroll position, the address bar and opening a link in a new tab all work by default on server-rendered pages. A single-page app has to implement each one.

→ Easy to miss until it breaks
XML is heavier than JSON

XML adds rules (schemas) and labels (namespaces and attributes) that JSON does not have, so it is larger. Banks and government systems still use it, for example in SOAP messages, which are an XML message format.

→ See "Payments and gateways". Larger on the wire, with stricter rules.
