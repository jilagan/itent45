Finding and fixing mistakes

A program can run without an error and still give a wrong answer. Debugging means finding the first step that went wrong, fixing it and testing other cases.

Your sinigang comes out too sour. You go back through the recipe card one step at a time and compare each step with what you did. At step 3 you find that the tamarind went in twice. Finding the step that went wrong is called debugging.

Think first. A recipe uses 2 cups of rice and 3 cups of water. A friend triples the rice and keeps the water. The rice comes out dry. Which step went wrong?
The water step went wrong. The rice amount was scaled and the water amount was left alone. The wrong result shows up at the end, and the cause sits in an earlier step.

A shop program should charge 120 pesos for each milk tea and take 10 percent off orders of 300 pesos or more. A bug hides in it. To trace the program, run it one step at a time for an order of 3 milk teas. Press Run next step, then press Wrong on the first step that gives a wrong result.

    Find the first wrong step

    Work from the start and check each result. The first wrong value points to the cause. A wrong value near the end can come from a mistake much earlier, so the last step is rarely the place to look. Checking each step of a written procedure is how you find the first wrong one.

    A fix that works for one order can fail for another. The rule is 10 percent off orders of 300 pesos or more. A test case is an order with its expected total. Pick a fix for step 3 and for step 4, then press Run tests to try six test cases.

    Good test cases

    Test a typical case, an empty case, a case at each boundary and a very large case. A boundary is a value where the rule changes, such as exactly 300 pesos. Mistakes often sit there. Rule tables, like those in Decision rules and tables, have many boundaries to test.

    Work from the start and stop at the first wrong value. Fix the step that caused it. Then test a typical order, an empty order and an order on each boundary, such as exactly 300 pesos. That order found a second bug that 3 teas missed.

    You can now trace a program to its first wrong result, choose a fix for the cause and test the fix on boundary cases.
