Case study: enlistment day

Picture the registrar's office on enlistment day. Thousands of students crowd around the schedule board, and each one only needs a few seconds to read it. Only one window can reserve seats, and it has to give the last seat in a section to exactly one student. A student enlistment system has the same two parts. The web tier is the group of servers that receive requests and build the pages. The database tier is the database that stores the seat counts. The one database that accepts changes is called the primary. Student systems like this have often run on a handful of application servers, usually Java programs, with a single relational database behind them. Many have since moved to cloud hosting, where capacity at the web tier can be bought in minutes. The slowdowns on enlistment morning have not gone away. "Scaling out with a load balancer" explained why: once the web tier is fixed, the database is the next bottleneck.

Think first A university can add web servers with a few clicks, yet its enlistment system is still slow at 8:00 AM. Which part of the system do you think is the limit, and why can more web servers not help it?
Ask for a show of hands: who has seen the enlistment system slow down on enlistment morning? Listen for students who blame the web servers, and steer them toward seat reservation.

The model assumes 15 requests per enlistment session, 3 of them reservations. Rates are in requests per second (rps) for the web tier and database operations per second (ops/s) for the database. Without staggering, the start bursts at about 6× the average rate, because everyone clicks at 8:00:00.

The shape is typical of student enlistment systems. Every number here is a teaching model, not a measurement of a real system.
