24 — Module 6 · monolith and microservices

Scaling out is not the same as splitting up

Panel 19 gave you six machines. Every one of them was an identical copy of the same application. That is a monolith, scaled horizontally. Most systems should be one. Splitting up is a different move on a different axis: several different things, each sized for its own appetite. Panel 20 already showed you a candidate, when browsing the catalog and reserving a seat turned out to want opposite things from the same box.

Ask the room If one part of your app needs 400 MB and the rest need 90, how much memory does a copy of the monolith need? Now multiply that by every copy you run.
Monolith · one app, many copies

Every copy can do everything

Any machine can serve any request, so the load balancer does not care which one it picks. Simple to deploy, simple to reason about, and one stack trace when something breaks. The cost: every worker must be sized for the heaviest thing it might be asked to do.

The question the memory graph cannot answer: do the parts talk?

Everything above assumed each request is served by one part. Real systems are rarely that clean: showing an enrolment page might need the catalog, the student record and the billing status. Inside a monolith those are function calls costing nothing. Across services each one is a network request, and they do not add up, they multiply.

How chatty is one request?
Each cross-service call costs about 3 ms more than the same work done in-process: connection, serialization, network, deserialization. That is on a good day, inside one datacentre.

Assume each service is up 99.9% of the time and has a slow moment 1% of the time. Those are respectable numbers for one service. Watch what they become when you need several of them to answer a single request.

The failure mode this describes has a name Splitting an application that still needs all its pieces on every request gives you a distributed monolith: you paid every cost of separation and kept every bit of the coupling. It is slower than what you started with, it fails more often than what you started with, and it is harder to debug than what you started with. Cut the boundary only where the parts truly do not need each other, which is a fact about your domain and not about your infrastructure. If two services call each other on every request, they were one service.
What to do in your capstone Build the monolith. Keep the parts cleanly separated inside it. Separate modules, no reaching into each other's tables. So that a boundary is there if you ever need to cut along it. Almost every microservices horror story starts with a team that split before they had a reason, and paid all four costs above to solve a scaling problem they did not yet have. Split when one part's appetite really is different from the rest, and you can say which part and why.
