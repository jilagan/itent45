Tool calls and the Model Context Protocol (MCP)

At a barangay hall, you do not walk into the records room yourself. You hand a request slip to the clerk at the front desk, and the clerk decides whether to fetch the record, ask for an ID or turn you down. A language model that uses tools works the same way. It does not run anything. It writes a tool call, which is a request in plain text, and a separate program decides whether to carry it out. This matters when you let an agent work on your files or database. An agent is a model that uses tools in a loop, as in "AI agents: the think, act and observe loop". In this panel, "server" has a different meaning from the Module 1 site, "What is a server?": here a server is a small program that offers tools, and a client is the part of your AI application that calls them.

Think first. A model produces only text. Between your question and the database, where could a person or a program stop a harmful request?

What the model was given
The box above is a tool description written in JSON, a plain-text format for structured data. It has a name, a one-sentence description, and the shape of the input the tool accepts (its schema). SQL is the language used to read and change database tables.

This is everything the model knows about the tool. It has never seen your tables, your rows or your server. It chooses a tool by reading the description, so a vague description leads to the wrong tool being called. That is a bug in the description, and the model is working as designed.
Why there is a standard for tools

Phone chargers used to differ by brand, so every phone needed its own cable. A shared plug solved that. AI applications have the same problem. Each one needs to reach the same systems: your files, your database, your issue tracker, your calendar. Without a common format, every pairing of application and system needs its own adapter, which is a piece of code that connects the two. The number of adapters multiplies.

One adapter per pairing
One shared standard

MCP, the Model Context Protocol, is a published standard that anyone can implement. Anthropic released it in November 2024 and other vendors adopted it. An MCP server is a small program that wraps one system and lists what it offers. An MCP client sits inside the application you are using. It asks the server for that list and passes the model's calls on. Write the server once and any client that follows the protocol can use it.

What MCP gives you A place to approve or refuse. Every call passes through the client before it reaches anything real, so approval, logging and refusal each have a place to happen.

A list you control. The model can only ask for tools it was offered. If it says it cannot read your file, the usual reason is that nobody gave it a tool that reads files.

Portability. The same server works in whichever editor or agent you move to next.

What it does not give you: judgment. A tool that deletes rows will delete rows whenever it is called correctly. MCP delivers the request. Deciding whether the request should have been made stays with you, and in an agent loop requests can arrive faster than you can read them.
