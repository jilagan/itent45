Choosing a relational or a document database

Think of two ways to keep student records. One is a set of spreadsheets with fixed columns, where the student sheet points to a course sheet. The other is a folder for each student, with everything about that student written on one page, including the course titles.

Databases come in both styles. A relational database, such as Postgres, stores data in tables with fixed columns, like the spreadsheets. A document database, such as Firebase, stores each record as one self-describing document, like the folder.

Both can store your capstone project. The right choice depends on which questions your app asks, so below the same enrollments are shown in both shapes and asked the same three questions.

Think first. Name a question your app asks on every page, and a question it asks once a semester. Which shape would you choose for each, and why?

The four families, and what "schema" means in each

A schema is the description of which fields each record has and what type each field is. The common split between SQL and NoSQL databases is a split in where the schema is enforced. Both families have a schema. In a relational database, the database enforces it. In the others, your code does.

Structured: the database enforces the schema
Relational

Tables with fixed columns and declared types. The schema is written down once, and the database rejects any data that does not fit it. Joins let you ask questions you did not plan for.

Postgres · MySQL · SQL Server · Supabase
Unstructured: your code enforces the schema
Document

Each record is a self-describing document. Two documents in the same collection can have different fields, so a typo creates a new field and no error is raised. The schema still exists, and it lives in your application code.

MongoDB · Firebase · DynamoDB
Unstructured: almost no schema
Key-value

A key, a value and nothing else. It is very fast and has no structure for asking questions. It is used more often as a cache in front of another database than as the main store of the data.

Redis · Memcached
Unstructured: built for connections
Graph

Stores relationships as records in their own right and does not use foreign keys. Use it when the main question is how one thing is connected to another across several steps, such as friends of friends.

Neo4j · Neptune
Document databases still need a data model The entities, attributes and relationships from "Entities and attributes" and "Relationships" still apply. A document database does not remove them. It moves the job of enforcing them from the database to your code, where every client has to remember the rules and nobody can see them in one place. This is sometimes a good trade. You still have to design the data.
What each shape does well
Rows suit questions you did not plan for

Any column can be filtered, joined or grouped later. You do not need to know the questions when you design the schema, and early in a project you do not.

→ the cost is a join, measured in "The N+1 query problem"
Documents suit one known question

The whole page comes back in one read, with no join and no assembly. This works well when the access pattern is fixed and known. It becomes painful the first time somebody asks a question the documents were not organized for.

→ the copied titles bring back the problem in "Normalization"
Rules about correctness

If the database itself refuses to sell the last seat twice, two students cannot both get it. Enforcing that rule in application code across several documents allows two requests to pass the check at the same time.

→ covered later in "Case study: enlistment"
Many systems use both

A common setup uses Postgres for data that must be correct and a faster store for data that must load quickly. This is a normal design.

→ it also means running two systems, as covered later in "Monolith or services"
Choosing for your capstone Start relational. Document databases are not worse. At your data volumes nothing you choose will be slow, and a relational design is easier to fix when you get the schema wrong. You will get it wrong at first. Being able to ask a question you had not thought of, without rewriting how everything is stored, is worth more in a semester project than any speed difference you could measure.
