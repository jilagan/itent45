One application or many services?

A small carinderia has one cook who prepares every dish. Any cook can handle any order, so when it gets busy you hire more identical cooks. A food court has a stall for each kind of food, each staffed for how busy that food is, and runners carry orders between the stalls.

Software has the same two designs. A monolith is one application that does everything. The identical machines in "Load balancers and scaling" were a monolith running as several copies. Microservices are several smaller applications, each doing one job and sized for its own load. The runners are like the network calls between services, and each call has a cost.

Most systems should be a monolith. "Case study: enlistment" showed one candidate for splitting: browsing the catalog and reserving a seat need opposite things from the same machine. This panel compares the memory each design needs and then lists what splitting costs.

Think first. One part of your application needs 400 MB of memory per worker, and every other part needs 90 MB or less. Every worker must be able to do everything, and you run 24 workers. How much memory do they need in total?

This section compares the memory needed by identical copies of one application with the memory needed by separate services.

Monolith: one application, many copies

Every copy can do everything

Any machine can serve any request, so the load balancer can pick any of them. The application is simple to deploy and easy to reason about, and a failure produces one stack trace (the error report that shows where in the code the failure happened). The cost is that every worker needs enough memory for the heaviest task it might be given.

What splitting costs

Each cost below repeats an earlier topic from this module, now inside your own system.

A function call becomes a network call

A call inside one program is now a request across the network. It can be slow, it can time out, and it can fail after the other service has already done the work.

See "Round trips and latency". The same delays now happen inside your own system.
Services get out of step

You cannot deploy all services at the same moment, so a change to a message must be additive: it adds a field and removes nothing. Your own services behave like old app versions that other services still depend on.

See "One API, many clients". Version drift now happens between your own services.
Every call needs retry rules

Each call needs a retry policy, a timeout, and an idempotency key (a unique ID that lets the receiver ignore a repeated request), so that a retry does not repeat the action. The payment gateway required the same.

See "Payments and gateways". The same rules now apply to calls you wrote yourself.
One failure appears in several logs

A single failure is spread across several services. To follow it, you need a shared trace ID: an identifier attached to every request so that logs from different services can be matched.

In "HTTP messages", you followed one request at a time.
Services that call each other

The memory comparison assumed that one part serves each request. Often several parts are needed. Showing an enrollment page might need the catalog, the student record and the billing status. Inside a monolith these are function calls that cost almost nothing. Across services, each one is a network request. The delays add up, and the chances of failure compound.

Choose how many calls one request makes
Each call to another service takes about 3 ms longer than the same work done inside one program. The extra time covers opening a connection, converting data to a message and back (serialization), and the network. That figure is for a good day inside one data center.

Assume each service is up 99.9% of the time, and that 1% of its calls are slow. Uptime is the share of time a service is working. These are good numbers for one service. See what they become when one request needs several services.

Distributed monolith Splitting an application whose parts still need each other on every request produces a distributed monolith. It has all the costs of separation and all the dependence between parts. It is slower, fails more often and is harder to debug than the single application you started with. Split only where the parts do not need each other. That depends on your business domain, not on your infrastructure. If two services call each other on every request, treat them as one service.
What to do in your capstone Build the monolith. Keep its parts separate inside it: separate modules, and no code that reads another module's tables. That way a boundary exists if you ever need to split along it. Most microservices failures start with a team that split before it had a reason, and paid the four costs above to solve a scaling problem it did not yet have. Split when one part's needs really differ from the rest, and you can say which part and why.
