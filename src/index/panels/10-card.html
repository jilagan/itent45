Relationships: one-to-one, one-to-many, many-to-many

A relationship links two entities, such as students and courses. Its cardinality decides which tables you need.

On a class list, each student has one ID card, a course has several sections, and many students take many courses. Counting how many sit on each side of a link gives its type: one-to-one, one-to-many or many-to-many.

Think first. If each student has one ID card and each course has many students, how would you store those two facts in tables?
Ask students to sketch the tables on paper before they open the next step. Most put a list of student ids in the course row, which a table column cannot hold.

Open each tab to see the tables that type needs. A table holds one entity. A primary key (pk) identifies each row, and a foreign key (fk) points to a row in another table.

What this type means for your tables

Neither the students table nor the courses table can hold the other's key, because each row would have to point at many rows. The extra table has one row for each pairing of a student and a course. It is also the only place for a date, a status or a grade, because those facts describe the pairing.
