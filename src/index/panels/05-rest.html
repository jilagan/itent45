HTTP verbs, URLs and status codes (REST)

When you order at a restaurant counter, the order slip says what you want done (place an order, change it, cancel it) and which order it applies to.

A web request works the same way. It carries a verb, such as GET or POST, that says what to do, and a URL that says what to do it to. A set of conventions for using verbs, URLs and status codes together is called REST.

Two terms describe what happens when a request is repeated. A verb is safe if it changes nothing on the server. It is idempotent if doing it twice leaves things the same as doing it once. GET, PUT, PATCH and DELETE make promises that POST does not. Pressing an elevator button twice is idempotent, because the second press changes nothing.

Think first. You submit an enrollment form and the page hangs, so you press refresh. Could you now be enrolled twice? Write down your answer and what you would need to know to be sure.

After you hand in an order slip, the kitchen sends something back: the food, a note that an item is sold out, or nothing because the kitchen is closed. A web server replies with a status code, a three-digit number that reports what happened to your request. The first digit tells you which kind of reply it is.

401 and 403

401 Unauthorized means the server does not know who you are. The name is misleading, because the real meaning is unauthenticated. Send your login details and try again.

403 Forbidden means the server knows who you are and still says no. Better credentials will not help, because you are not allowed.

404 and 500

404 and 500 both look like a broken page to a user, but they point to different places to look.

404 means the URL names nothing, so check the request, the path and the id. 500 means the server code failed with an error, so read the server's error report (called a traceback) and ignore the page itself.

A URL should name a thing, such as courses or students, and the verb says what to do with it. A common first mistake is to put the action in the URL. This section covers how to name URLs and how much data one request should return.

Naming URLs
✕ Verbs inside the URL
  • GET /getCourses
  • GET /createEnrollment?student=5
  • POST /updateCourseName
  • GET /deleteStudent?id=5

Every new action needs a new URL, so the list keeps growing. The fourth one also changes data behind a GET. A search engine crawler (a program that follows links) could delete your students.

✓ Nouns in the URL, verb in the method
  • GET    /courses
  • POST   /enrollments
  • PATCH  /courses/ITENT45
  • DELETE /students/5

A small fixed set of verbs works with a growing set of nouns. Anyone who knows HTTP can guess your URLs without reading documentation. A predictable URL scheme is one of the main benefits of REST.

One request or fifty?

A page lists a student's enrollments and needs the course title for each one. You can fetch the list and then fetch each course in turn, or you can design an endpoint (a URL the server answers) that returns everything in one request. A round trip is one request and its reply, and "Round trips and latency" shows what each one costs. A handler is the code on the server that answers one request.

When fetching everything is wasteful

The previous section fetched fifty courses because the page needed all fifty. Many lists are different. A course catalog has five hundred entries and a student scrolls past a dozen. Fetching all of them in one request is efficient per item but wasteful overall, and the first screen waits for data nobody asked to see.

Choosing how much an endpoint returns Both designs fail for the same reason: the endpoint was designed without knowing what the page does with it. One request per item costs a round trip each. One request for everything moves data nobody scrolls to. In both cases the fix is to add a parameter to the endpoint. GET /courses?codes=ITENT45,CSCI21 returns exactly the missing pieces in one trip. GET /enrollments?include=course lets the caller choose how much detail to receive. GET /courses?limit=20&offset=40 lets the caller ask for one slice, which is called pagination.

To decide, ask how many of the returned items will be looked at, and how soon the reader needs the first one. If every client loops over your list endpoint to fill in gaps, the endpoint returned too little. If most of what you send is never scrolled to, it returned too much.
What REST asks of you Model your system as resources: the nouns your users talk about, such as courses, enrollments and students. Give each resource a URL. Act on resources with the standard verbs. Let the status code report the outcome. Keep each request self-contained, so the server does not need to remember the previous one. This is called being stateless. Stateless servers are easier to copy onto many machines, as covered later in "Load balancers and scaling".
