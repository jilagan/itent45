The three tiers of a web application

A web application is split into three parts, called tiers. Each tier has one job and runs in a different place.

In a restaurant, the customer never walks into the kitchen. The customer tells a waiter what they want. The waiter fetches it from the kitchen and brings it back.

Think first. Take the list of courses you are enrolled in. Which part produced it: the browser, the application server or the database? Write down your guess.
Most students cannot say which tier produced a given part of a page. The trace in "Follow one request" fills that gap. Ask a few students for their answers before anyone presses Play.

Every web application has these three tiers. Read the cards from left to right: the user's device, your server, then the database.

Tier 1

The browser

Presentation tier

Shows the page. Runs on the user's device, which you do not control.

Tier 2

The application server

Application tier

Applies the rules and holds the database password. Runs on your server.

Tier 3

The database

Data tier

Stores the data in tables. Only the application server may ask it questions.

More detail

Each tier is built with different tools. A framework is a ready-made toolkit for building the application tier. Pick one to see what you would write and where each tier runs. The steps a request takes are the same in every framework.

Suppose the browser could talk to the database directly. The password would then sit in code on the user's laptop, where anyone can read it and run any query. In the restaurant, a customer would be in the kitchen. So only the application tier holds the password, and it decides which requests the database may answer.

You can now say which tier should hold the database password and why.

More detail

AI tools can write much of this code for you. You still need to know where each tier runs and what passes between them, because that tells you where a check must happen. The browser is on a device the user controls, so a check made only there can be skipped.
