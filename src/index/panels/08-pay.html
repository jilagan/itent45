08 — E-commerce · your server becomes a client

Checkout, where your API is the one doing the asking

Up to now your server has answered requests. In a checkout it also sends them, to a payment gateway like PayMongo, Stripe or Xendit, over the same HTTP, with the same verbs and status codes you saw in panel 04. Nothing new to learn. What is new is that three parties now hold pieces of one transaction, and each of them can fail separately.

Ask the room When you type your card number into a checkout page, which machines does that number touch on its way to the bank? Most people guess wrong, and the right answer is the reason online shops are not constantly leaking cards.

Step 1

Why the card skips your server The browser sends the card straight to the gateway and gets back an opaque token. Your server only ever handles that token. This is deliberate: the moment card numbers touch a machine you own, that machine falls inside PCI DSS scope, and so does every system it talks to. Handling a token instead keeps that burden with the people whose entire business is carrying it.
Roles invert at step 8. The gateway calls you. Your API is the server in that conversation, and the signature header is the only thing standing between you and anyone on the internet marking their own order paid.
Why is every message in that flow JSON?

Nothing in this exchange is ever looked at by a person. Two programs at two companies are stating facts to each other. That is the situation JSON was shaped for, and it is worth seeing the alternatives written out before accepting it. Here is the same charge request, three ways.

When XML is still the right answer JSON carries values. It has no way to state that amount must be a positive integer, or that currency must be a real ISO code, so every one of those checks lives in somebody's application code and gets written again on both sides. An XML schema states them once and a parser enforces them before your code runs, and XML-DSig can sign the document itself rather than the bytes around it. When the thing being exchanged is money between institutions, that is worth six times the payload. Several Philippine banks still expose exactly this, so if your capstone touches a real bank rather than a modern gateway, expect SOAP and budget a week for it.

handler 40 ms + gateway 800 ms = 840 ms 4 workers ÷ 0.840 s = 4.8 rps
Charging on a queue, confirming by webhook
handler 40 ms, gateway call moved off the path 4 workers ÷ 0.040 s = 100 rps

Every third-party call you make inside a request becomes part of your handler time, which means their bad afternoon becomes your outage. Twenty times the capacity here comes from moving the call off the request path. The same move that fixed Card C in the breakout.
