06 — Why REST is worth the trouble

One backend, three clients that have never met

A web page, an iPhone app and an Android app can all be built against the same API without any of them knowing the others exist. The server does not check who is calling. It receives a request for a resource and returns a representation of it, and every client renders that however it likes.

This is what the name means REST stands for Representational State Transfer. The server holds state. When you ask for it you get a representation of that state: JSON text, in this case. What you do with it is your business. Render it as a table, a list, a native scroll view, or a printout. The server never needed to know.
THE COUNTEREXAMPLE IS THE SITE YOU USE EVERY DAY

A server-rendered system has no API layer, and that is why this is hard for it

Systems like it were servlet-based, from an era when that stack was what you chose. The server does not return data. It returns a finished page. Tier 1 and tier 2 exist as separate machines but are welded together in the code, because the business logic lives inside the thing that generates the markup.

What an API would return JSON
Same data. Only one of them can serve a phone.

Everything a mobile app needs is in the left-hand response, tangled up with table widths, CSS class names and a decision about column order. An iOS app cannot use any of it without scraping, parsing HTML meant for a browser and hoping the layout never changes. It always changes.

This was not a mistake. One client, browsers only, and server-rendered HTML was the fastest correct answer available. The cost only appears years later, when a second kind of client turns up and there is nothing for it to call. Retrofitting an API means going into those page-generating classes and pulling the logic back out of the markup. "It already works, why change it" is a harder argument to answer than it sounds.

WHAT SERVING THOSE THREE CLIENTS COSTS YOU

Once phones call your API, you cannot change it freely

That is the bill for everything above. Serving clients you do not control means you no longer control when they update. Web users get new code on their next reload. Someone with your iOS app has to visit the store and choose to update, and some of them never will. So old copies keep calling your API for months. The rule this leads to On an API with clients you cannot update: add freely, remove almost never. When you truly must break something, publish it at a new path (/api/v2/courses) and keep the old one answering until the tail is thin enough to accept, or leave the old field in place alongside the new one and stop documenting it.
