Finding and fixing mistakes

A program can run without an error and still give a wrong answer. Debugging means finding the first step that went wrong, fixing it and testing other cases.

In an online store, you order 3 milk teas at 120 pesos each. The store takes 10 percent off orders of 300 pesos or more, so the total should be 324 pesos. The checkout shows a different total. The mistake sits in one of the steps that computed it. Finding that step is called debugging.

Think first. The checkout page shows a wrong total, and the program behind it ran five steps. Which step would you check first, and why?
Many students start at the last step because that is where the wrong total shows. The cause usually sits in an earlier step, so start at the first step and check each value.

The store's program should charge 120 pesos for each milk tea and take 10 percent off orders of 300 pesos or more. A bug hides in it. To trace the program, run it one step at a time for an order of 3 milk teas. Press Run next step, then press Wrong on the first step that gives a wrong result.

    Find the first wrong step

    Work from the start and check each result. The first wrong value points to the cause. A wrong value near the end can come from a mistake much earlier, so the last step is rarely the place to look. Checking each step in turn, as in Writing steps for a robot, is how you find the first wrong one.

    A fix that works for one order can fail for another. The rule is 10 percent off orders of 300 pesos or more. A test case is an order with its expected total. Pick a fix for step 3 and for step 4, then press Run tests to try six test cases.

    Good test cases

    Test a typical case, an empty case, a case at each boundary and a very large case. A boundary is a value where the rule changes, such as exactly 300 pesos. Mistakes often sit there. Rule tables, like those in Decision rules and tables, have many boundaries to test.

    Work from the start and stop at the first wrong value. Fix the step that caused it. Then test a typical order, an empty order and an order on each boundary, such as exactly 300 pesos. That order found a second bug that 3 teas missed.

    You can now trace a program to its first wrong result, choose a fix for the cause and test the fix on boundary cases.
