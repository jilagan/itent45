Building the page: on the server or in the browser

A restaurant can print a fresh menu for every customer, or hang one menu board and change only the prices that change.

A web server faces a similar choice. In "One API, many clients" the server sent data as JSON, and someone still has to assemble the page that a person looks at. Building it on the server is called server-rendering. Building it in the browser is called a single-page app.

The choice changes what travels over the network, how fast the first screen appears, and how much work your server does for each visitor. This panel compares the two models and what each one costs.

Think first. When you click a link on a website, does the browser replace the whole page or only part of it? Open a site you use and watch the browser tab for a loading spinner. What did you see?
On some sites the whole page reloads and on others it does not. Ask students to name one site of each kind and say how they could tell.
Server-rendered page (older model)

Every click fetches a whole new page

The server fills in a template (a page layout with blanks), produces finished HTML (the language that describes a web page), and sends a complete document. The browser discards the old page and draws the new one. The enlistment system works this way.

click → request → server renders → full HTML → repaint first screen: fast, the HTML arrives ready to draw each later click: another full page
Single-page app (newer model)

One page, then only data moves

The first load fetches an almost empty shell and a large bundle of JavaScript (code that the browser runs). After that, each click fetches JSON, and the browser updates only the parts of the DOM that changed. The DOM is the browser's live model of the page. Nothing else reloads.

first load → shell + bundle → fetch JSON → build DOM first screen: slower, nothing shows until the bundle runs each later click: a few KB of JSON and no redraw of the rest
The same two courses in three formats

The information is the same each time: eight values, 49 characters of data. Only the packaging differs. JSON and XML are text formats for data, and XML wraps every value in named tags. HTML is the format for web pages. Sizes are in bytes, and 1,000 bytes is about 1 KB (a kilobyte).

What each choice costs elsewhere
Rendering moves to the user's device

A single-page app has the browser build the page, so your server no longer does that work. That raises the capacity ceiling covered later in "Server capacity", using hardware you did not buy.

→ Covered later in "Server capacity". It uses the user's battery.
The first screen is slower

Server-rendered HTML is ready to draw when it arrives. A bundle has to download, load and run before anything appears, and then it fetches its data.

→ See "Round trips and latency". The cost is now on the client.
You rebuild what the browser did for free

The back button, scroll position, the address bar and opening a link in a new tab all work by default on server-rendered pages. A single-page app has to implement each one.

→ Easy to miss until it breaks
XML is heavier than JSON

XML adds rules (schemas) and labels (namespaces and attributes) that JSON does not have, so it is larger. Banks and government systems still use it. An example, covered later in "Payments and gateways", is a SOAP message, which is an XML message format that banks use.

→ Covered later in "Payments and gateways". Larger on the wire, with stricter rules.
What to pick for your capstone If your project is mostly pages that people read, server-rendered pages have fewer parts and a faster first screen, and Django (a Python web framework) builds them by default. If it is a tool that people use for twenty minutes, clicking around, the bundle's download cost is made up after several pages, about seven in the model above. Most student projects are the first kind and get built as the second kind, because tutorials show that approach. Choose based on how long users stay and how many pages they open.
