HTTP verbs, URLs and status codes (REST)

A web request carries a verb that says what to do and a URL that says what to do it to. The server replies with a status code.

At a restaurant counter, the order slip says what to do (place, change or cancel) and which order it applies to. A web request has the same two parts, a verb and a URL. Place the same order twice and you get two meals. Cancel it twice and it stays cancelled.

Think first. You submit an enrollment form and the page hangs, so you press refresh. Could you now be enrolled twice? What would you need to know to be sure?

Course code and id

Each row has two identifying fields. The code is what people read, such as ITENT 45. The id underneath it is what the URL uses, such as ITENT45. The id is the code with spaces removed, because a space cannot appear in a URL unless it is written as %20. The server stores both when it creates the course, and the id never changes after that.

One request or fifty?

A page lists a student's enrollments and needs the course title for each one. You can fetch the list and then fetch each course in turn, or you can design an endpoint (a URL the server answers) that returns everything in one request. A round trip is one request and its reply, and "Round trips and latency" shows what each one costs. A handler is the code on the server that answers one request.

When fetching everything is wasteful

The first widget fetched fifty courses because the page needed all fifty. Many lists are different. A course catalog has five hundred entries and a student scrolls past a dozen. Fetching all of them in one request is efficient for each item and wasteful overall, and the first screen waits for data nobody asked to see.

Choosing how much an endpoint returns

Both designs fail for the same reason: the endpoint was designed without knowing what the page does with it. One request per item costs a round trip each. One request for everything moves data nobody scrolls to. In both cases the fix is to add a parameter to the endpoint. GET /courses?codes=ITENT45,CSCI21 returns exactly the missing pieces in one trip. GET /enrollments?include=course lets the caller choose how much detail to receive. GET /courses?limit=20&offset=40 lets the caller ask for one slice, which is called pagination.

To decide, ask how many of the returned items will be looked at, and how soon the reader needs the first one. If every client loops over your list endpoint to fill in gaps, the endpoint returned too little. If most of what you send is never scrolled to, it returned too much.

Two properties tell you how risky a verb is to repeat. A verb is safe if it changes nothing. It is idempotent if sending it twice gives the same result as sending it once. Select each verb and read what happens when you send it twice.

Naming URLs

A URL should name a thing, such as courses or students, and the verb says what to do with it. A common first mistake is to put the action in the URL.

✕ Verbs inside the URL
  • GET /getCourses
  • GET /createEnrollment?student=5
  • POST /updateCourseName
  • GET /deleteStudent?id=5

Every new action needs a new URL, so the list keeps growing. The fourth one also changes data behind a GET. A search engine crawler (a program that follows links) could delete your students.

✓ Nouns in the URL, verb in the method
  • GET    /courses
  • POST   /enrollments
  • PATCH  /courses/ITENT45
  • DELETE /students/5

A small fixed set of verbs works with a growing set of nouns. Anyone who knows HTTP can guess your URLs without reading documentation. A predictable URL scheme is one of the main benefits of REST.

What REST asks of you

REST is a set of conventions for using verbs, URLs and status codes together. Model your system as resources: the nouns your users talk about, such as courses, enrollments and students. Give each resource a URL. Act on resources with the standard verbs. Let the status code report the outcome. Keep each request self-contained, so the server does not need to remember the previous one. This is called being stateless. Stateless servers are easier to copy onto many machines, as "Load balancers and scaling" shows.

Full example requests

GET /courses/ITENT45 HTTP/1.1 POST /enrollments HTTP/1.1 Content-Type: application/json {"student":"20-1234","code":"ITENT 45"} PUT /courses/ITENT45 HTTP/1.1 Content-Type: application/json {"title":"App Dev and Emerging Tech","units":3} PATCH /courses/ITENT45 HTTP/1.1 Content-Type: application/json {"units":6} DELETE /enrollments/8891 HTTP/1.1

POST needs protection that you build, such as a unique constraint (a database rule that rejects duplicates) or an idempotency key (a unique code the client sends with each request). "Payments and gateways" shows the second one at work.

After you hand in the order slip, the kitchen replies with the food, a note that an item is sold out, or nothing because it is closed. A web server replies with a status code. The first digit says which kind of reply it is.

1xx
Informational
The server is still working. You will rarely see these.
2xx
Success
The request worked. The codes differ in what came back.
3xx
Redirect
Go to another URL, or use the copy you already have.
4xx
Client error
The request was wrong. The server is working. Fix the request.
5xx
Server error
The request was fine. The server failed. Its logs show why.

Two pairs that are easy to mix up

401 and 403

401 Unauthorized means the server does not know who you are. The name is misleading, because the real meaning is unauthenticated. Send your login details and try again.

403 Forbidden means the server knows who you are and still says no. Better credentials will not help, because you are not allowed.

404 and 500

404 and 500 both look like a broken page to a user, and they point to different places to look.

404 means the URL names nothing, so check the request, the path and the id. 500 means the server code failed with an error, so read the server's error report (called a traceback) and ignore the page itself.
