Relationships: one-to-one, one-to-many, many-to-many

On a class list, one student can take several courses, and every course has several students on its list.

The number of items that can sit on each side of a link between two entities is called cardinality. There are three kinds: one-to-one, one-to-many and many-to-many.

Each kind produces a different set of tables, where a table is a grid of rows and columns that holds one entity, like one sheet of a spreadsheet. If you choose the wrong kind on the diagram, you find out later, when somebody needs a second value in a place that allows only one.

Think first. Suppose each student has exactly one student ID card, and each course has many students. How would you store these two facts in tables? Sketch your tables, then open the tabs below and compare.

Why many-to-many needs a third table The extra table in a many-to-many relationship is the only place where a date, a status or a grade can be stored, because those facts describe the pairing and belong to neither side. "Entities and attributes" treats Enrollment as an entity for the same reason. A many-to-many link on a diagram is a sign that a table is missing.
