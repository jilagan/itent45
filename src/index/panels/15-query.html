The N+1 query problem

Picture asking a clerk for 50 files. You can ask for them one at a time, and the clerk walks to the cabinet 50 times. Or you can ask for all 50 at once, and the clerk makes one trip with a cart.

A web page that lists 50 enrollments with their course titles can behave either way. A query is one request to the database. In "Normalization" the course title moved into its own table, so the page must fetch the title from that table for every row.

The slow pattern is called the N+1 query problem. This panel measures what it costs as the page gets longer.

Think first. A page shows fifty enrollments with their course titles. The template reads the course title from each enrollment, and the courses were not loaded in advance. How many times is the database queried? Write down your number before you use the slider.
The code that builds the page
The code above is Django. The view (views.py) fetches rows from the database. The template (schedule.html) is the page layout, and it loops over the rows.

The model assumes each query takes 0.4 ms (milliseconds), because the database can answer it from an index, which is a lookup structure like the index of a book. It also assumes 24 ms of handler time that is not database work. Handler time is the total time the server spends on one request. A worker is a server process that handles one request at a time, and the ceiling is the most requests per second (rps) that 8 workers can finish.

Why testing does not catch this With three rows in your development database, the loop makes four queries and takes about 1.6 milliseconds, which you cannot notice. The number of queries grows with the number of rows, and test data rarely has enough rows. The problem appears only in production, the live system, where the data is large and your tests do not run.
