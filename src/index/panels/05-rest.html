05 — Verbs & REST

The verb says what you want done. The URL says what to do it to.

Every request carries a verb. Django's request.method is that verb, and most of the design mistakes people make come from ignoring what each one promises. Two promises matter: whether it changes anything, and whether doing it twice differs from doing it once.

Ask the room. You submit a form, the page hangs, you hit refresh. Have you now enrolled twice? The answer depends entirely on which verb that form used.

The other half of the sentence: what came back

The verb says what you wanted. The status code says what happened. You only need to remember one thing to read them: the first digit tells you whose problem it is.

1xx
Hold on
Still working. You will almost never see these.
2xx
It worked
Did what you asked. The differences are about what came back.
3xx
Look elsewhere
Go to another URL, or use the copy you already have.
4xx
Your fault
The request was wrong. The server is healthy. Fix the request.
5xx
Their fault
The request was fine. The server broke. Read the server logs.

THE PAIR EVERYONE MIXES UP

401 Unauthorized is badly named. It means unauthenticated. The server does not know who you are. Send credentials and try again.

403 Forbidden means the server knows exactly who you are, and the answer is still no. Better credentials will not help; you simply are not allowed.

THE FORK THAT SAVES YOU AN HOUR

404 and 500 look equally broken to a user, and they send you to completely different places.

404 means your URL named nothing, check the request, the path, the id. 500 means your code raised an exception, stop reading the front end and go and read the traceback.

Naming things: the mistake almost everyone makes first
✕ Verbs baked into the URL
  • GET /getCourses
  • GET /createEnrollment?student=5
  • POST /updateCourseName
  • GET /deleteStudent?id=5

Every new action needs a new URL, so the list grows without end. Worse, the fourth one changes data behind a GET. So a search engine crawling your site can delete your students.

✓ Nouns in the URL, verb in the method
  • GET    /courses
  • POST   /enrollments
  • PATCH  /courses/ITENT45
  • DELETE /students/5

A small fixed set of verbs against a growing set of nouns. Anyone who knows HTTP can guess your API without reading documentation. That guessability is most of what REST is worth.

One request or fifty? How much should an endpoint return

A page lists a student's enrolments and needs the course title for each one. You can fetch the list, then loop and fetch each course, or you can design an endpoint that returns the whole thing once. Panel 02 showed what a round trip costs. This is the same bill, arriving at the API design.

Modelled at 38 ms round trip, about 700 bytes of request headers each time (cookies, user agent, accept), and 120 bytes per course.

Over HTTP/1.1 a browser opens six connections to one host and no more, so fifty-one requests queue up in batches of six. Turn HTTP/2 on and watch which number moves and which one does not.
And the reverse: when fetching everything is the waste

That comparison quietly assumed the page needs all fifty. Most lists are not like that. A course catalog has five hundred entries and a student scrolls past a dozen. Fetching the lot in one trip is efficient per item and enormously wasteful overall, and it makes the first screen wait for data nobody asked to see.

Drag it all the way right, to the student who reads every single course. Even then, look at which row still favours loading as they scroll, and ask what your users actually do.
The answer is usually neither extreme Two failure modes, opposite directions, same cause: designing the endpoint without knowing what the page does with it. One request per item pays a round trip for each. One request for everything pays for data nobody scrolls to. The fix in both cases is a parameter rather than a new endpoint. GET /courses?codes=ITENT45,CSCI21 fetches exactly the missing pieces in one trip. GET /enrollments?include=course lets the caller say how much detail it wants. GET /courses?limit=20&offset=40 lets it ask for a slice.

The question that settles it is how many of the things you return will actually be looked at, and how soon the reader needs the first one. If every client immediately loops over your list endpoint to fill in gaps, it returned too little. If most of what you send is never scrolled to, it returned too much.
What REST actually asks of you Model your system as resources. The nouns your users talk about: courses, enrollments, students. Give each one a URL. Act on them with the standard verbs. Let the status code carry the outcome. Keep each request self-contained, so the server needs no memory of the last one. Which is the same statelessness that panel 19 shows you cannot scale without.
