The N+1 query problem

A page that lists 50 enrollments can ask the database 51 questions or 1 question. The number of queries decides how fast the page is.

Picture asking a clerk for 50 files. You can ask for them one at a time, and the clerk walks to the cabinet 50 times. Or you can ask for all 50 at once, and the clerk makes one trip with a cart. A web page that lists 50 enrollments with course titles can behave either way.

Think first. A page lists fifty enrollments. For each row, the page looks up the course title separately. How many times is the database queried? Write down your number.
The usual answer is 50. The correct answer is 51, because the page first runs one query to fetch the enrollments. Collect numbers before anyone moves the slider.

Start with One query per row and move the slider. This slow pattern is the N+1 query problem. Then try One join and a cache, and compare.

How the times are worked out

The model assumes each query takes 0.4 ms (milliseconds), because the database can answer it from an index, which is a lookup structure like the index of a book. It also assumes 24 ms of handler time that is not database work. Handler time is the total time the server spends on one request. A worker is a server process that handles one request at a time. The most pages per second is the number that 8 workers can finish.

When a cache is a poor choice

A cache works well when the table is small and rarely changes. When the data changes often, you hold two copies of the same fact and one of them goes out of date. "Normalization" describes the same problem.

With three rows in your test database, the page makes four queries and takes about 1.6 milliseconds, which nobody notices. The number of queries grows with the number of rows, and test data rarely has enough rows. The problem appears only in production, where the data is large and your tests do not run.
