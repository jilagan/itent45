Normalization: storing each fact once

Suppose you keep a class list in Excel and type the course title on every student's row. When the course changes its title, you have to fix every row, and if you miss one, the sheet holds two titles for the same course.

The better layout is a second sheet that lists each course once, with each student row pointing to it. In a database this is called normalization: store each fact once and point to it from everywhere else. A table is a grid of rows and columns, like one sheet.

Below, the same enrollments are stored two ways, as one flat table that holds everything and as two linked tables.

The flat table repeats the title once for each enrollment. The split version stores it once and points to it.

Both designs are valid. The flat table can show one student's schedule without a join, which is a query that combines rows from two tables. People propose it for that reason. Changing a course title in the flat table costs one write for each enrollment.
The rule behind normalization Store each fact once, and point to it from every place that needs it. A title stored in one row has one value. A title stored in four hundred rows can have different values in different rows, and nothing in your code will notice, because each of those rows is valid on its own. The split design prevents that failure. A schema generated by an AI tool can work and still have this problem, and the tool will not warn you.
