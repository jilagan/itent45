One API for the web, iOS and Android

A website, an iPhone app and an Android app can all use one backend. They reach it through an API. The server does not care which one is calling.

A restaurant kitchen can serve dine-in customers, the drive-thru window and a delivery app. It prepares the same order for all three, and each channel presents it in its own way. A website, an iPhone app and an Android app can share one backend in the same way.

Think first. A university has a web API that returns course data. It now wants an Android app. Which parts of the backend must be rewritten?
For the web API the answer is that the whole backend is reused. The real enlistment system returns finished web pages, so the answer there is much less. Ask students to explain the difference after the step "A system with no API".

What REST stands for

REST stands for Representational State Transfer. The server holds the data. When a client asks for it, the server sends a representation of that data, which here is JSON text. What the client does with it is up to the client: a table, a list, a scrolling view in a phone app, or a printout. The server never needs to know.

Older systems, such as the enlistment system, are server-rendered. They return finished web pages, with the data mixed into the layout. A phone app cannot use that page directly. Compare what each kind of system returns.

The same data in two forms

All the data a mobile app needs is in the HTML reply, mixed with table widths, CSS class names (labels that control appearance) and a decision about column order. An iOS app cannot use that reply directly. It would have to scrape it, which means reading HTML written for a browser and hoping the layout never changes. The layout changes often.

Why teams build it this way

With one kind of client, browsers only, server-rendered HTML was the fastest correct design. The cost shows up years later, when a second kind of client arrives and there is nothing for it to call. Adding an API later means going into the page-generating code and pulling the business logic (the rules for what the system does) out of the markup. Teams often keep the old design because it still works.

The answer to the Think first question for the enlistment system is much less. There is no separate layer that a mobile app could call, because the data and the layout are mixed in one reply. Ask students how much of the backend a new mobile app could reuse before they open the comparison.

Rule for changing an API

If you cannot update the clients, add freely and remove almost never. When you must break something, publish the new version at a new path (/api/v2/courses) and keep the old one running until few users remain on old versions. Another option is to keep the old field next to the new one and stop documenting it.
